# 状态订阅优化对比

日期：2026-10-14，北京时间。原始时间戳以 JSON 中的 UTC 为准。

## 结论

在本次三档、各三轮的真实鼠标拖拽中，外层 `App` 提交次数每轮从 60 降到 1，减少约 98.3%。剩下的一次来自拖拽结束后的待保存状态更新。计数来自生产包中的 effect，每次已提交渲染增加一次，不是整棵 React 树的渲染次数，也不是 CPU 耗时。

两版拖拽帧率均已接近 60 FPS，没有测出明显的帧率提升。这里能确认的是无关页面更新减少，不能把提交次数下降换算成同等比例的性能提升。

## 环境与方法

- Windows 10.0.26200，Intel Core i7-12700H，20 个逻辑核心，16 GB RAM。
- Edge 155.0.4283.45，headless；1920×1080 CSS 视口，devicePixelRatio=1。
- Node.js 22.22.3，生产构建，使用本机 preview 服务；视口裁剪开启，详情模式。
- 100 / 1,000 / 10,000 节点；每档拖拽与平移各三轮，共 18 组样本 / 版本。
- 素材复用六张 SVG 封面和一个视频，本次采样期间不导入新媒体，不打开播放器。
- 每轮先定位 `node-3` 并等待视口与保存稳定，随后执行 60 次鼠标移动，每次等待 16 ms。该等待不是对鼠标事件频率或显示刷新率的保证；实际帧间隔由 requestAnimationFrame 记录。
- 每轮丢弃最初两个帧间隔，其余逐帧原值保留。平均 FPS 按保留帧数 / 保留间隔总和计算，P95 为排序后 floor(0.95×样本数) 处值。
- 每轮结束挂载 12～13 张卡片；此结果不代表同时挂载万张媒体卡片或解码万份独立文件。
- 原版：Git 基线 `41a2234` 加同样的诊断计数，构建 JS `index-BENZNfwv.js`。最终优化版为源码提交 `66fd8db`，采样使用 `index-BF8fCY0r.js`，原始报告保留了 bundle URL。

本次各轮按顺序执行，没有交错随机化。后台系统任务和浏览器调度会影响小幅差异，因此不据此声称统计显著的帧耗时改善。

## 复测

当前版：先运行 `npm.cmd run check` 与 `npm.cmd run preview`，另开终端：

```powershell
$env:BENCHMARK_LABEL = "current"
node scripts/interaction-benchmark.mjs
```

原版：在独立目录检出 `41a2234`，复制当前 `scripts/interaction-benchmark.mjs`，并为原 `App.tsx` 添加相同计数：模块中 `let appCommits = 0;`；`App` 内添加无依赖 effect 执行 `appCommits++`；`frameDiagnostics` 返回值增加 `appCommits`、`buildMode: import.meta.env.MODE`、`culling: useGraph.getState().culling`。然后安装锁文件依赖、构建、启动 preview，以 `BENCHMARK_LABEL=baseline` 运行脚本。

每次脚本自动创建新的 `benchmark-*` 工作区。`BASE_URL` 可指定已有 preview 地址。图形环境不同或生产包改变时，应重新采样并保存自己的环境信息。
