## 案例一：从订阅边界定位拖拽更新

观察：原 `App` 订阅整个节点数组，节点移动会使外层页面重新执行。详情和预览在 store selector 内用 `find()` 扫描节点数组。

假设：把完整数组订阅移到画布，外层订阅数量等具体字段，可以减少与拖拽无关的页面提交。

实现：提取 `GraphCanvas`、`Inspector`、`MediaPreview`、`Thumbnail`、`Performance`。按 ID 保存数组位置索引，位置改变时直接读取当前数组中的节点，不重建索引。组件仍按原有职责保留媒体清理和按需加载。

验证：在生产包中用 effect 计数外层界面已提交的更新。对 100 / 1,000 / 10,000 节点各做三轮真实鼠标拖拽，每轮 60 次移动；原版每轮 60 次外层提交，优化后每轮 1 次，来自拖拽结束后的待保存状态变化。帧率、P95 和原始样本见 [性能对比](performance/COMPARISON.md)。

决策：保留 React Flow 需要的节点数组与引用语义；索引只解决 ID 查找，不声称整条拖拽路径变成 O(1)。现有 `applyNodeChanges` 仍需处理数组，Canvas 仍须更新。

## 案例二：让异常恢复行为可测试

观察：原恢复流程主要核对节点数。未知版本、悬空边、环或缺失元数据可能进入渲染路径；加载失败后生成的临时示例还可能触发增量写入。

先定义用例，再补实现：新增恢复测试的首次运行共 39 项、21 项失败，原因包括验证器尚未实现和旧恢复逻辑接受损坏记录。随后添加纯函数 `validateGraph()`，在同一只读事务中恢复并检查图版本、元数据和结构。校验采用迭代遍历，对万节点长链也不会递归溢出。

恢复失败时，保留原记录，将临时示例与持久化隔离；用户确认重新生成后才恢复保存。浏览器验收会在新的工作区故意写入未知版本，再验证临时拖拽和保存按钮不会修改原图记录。

保存时序测试使用可控 Promise：暂停第一次事务 → 产生新节点位置和视口 → 完成旧事务 → 检查状态仍待保存 → 第二次事务保存新值。这个用例验证了最终数据与中间状态。

## 本轮对 AI 产出的纠正

- 保存提示测试的初稿使用“已保存在本地”作为匹配串，但旧文案是“并保存在本地”，可能漏掉问题。审查后将断言改为检查“保存在本地”，并验证事务后的实际记录。
- 组件抽取脚本一次截取了错误的 JSX 边界，TypeScript 构建发现画布返回表达式缺失；补回明确的 React Flow 配置后才继续浏览器验证。
- 首次完整浏览器验收在总览定位 `node-9999` 时超时。截图最终已出现目标，但动画过程中响应延迟明显；尚未用 trace 确定来源。后续让总览切换与远距离定位直接跳转，保留近距离动画，并重新验收完整流程。首次失败报告保留在 [navigation-timeout.json](performance/navigation-timeout.json)。
- 审查浏览器报告时发现，连续重新生成相同规模的数据集，旧节点数和旧“已保存”状态可能让脚本提前通过等待。验收等待现同时检查切换已结束，避免将旧图状态计入新一轮测量。
- 没有在每帧构造新的节点 Map；测试检查索引稳定、移动后的查找正确，以及未变化节点对象引用稳定。

这些纠正说明，测试断言、类型检查和实际交互都需要审查，AI 的第一次输出不能直接视为完成。

## 持续检查与展示路径

`npm.cmd run check` 执行单元测试与生产构建，GitHub Actions 复用同一入口。远端工作流尚需上传仓库后实际运行。真实浏览器验收使用 `npm.cmd run test:e2e`，独立采样使用 `node scripts/interaction-benchmark.mjs`。

建议面试演示按以下顺序：

1. 定位深层节点，拖拽、重连并刷新，说明完整数据与可见投影的关系。
2. 打开性能对比，解释为什么选择提交次数、P95 和原始样本，并讲清测量条件。
3. 展示 `validateGraph()` 与保存时序用例，说明错误数据和异步竞态如何受到控制。
4. 展示 Git diff、检查入口及上述实际纠错过程，说明 AI 如何参与实现与验证。

本轮交付体现 AI 辅助开发流程；自然语言图谱助手仍属于后续功能。面试讲解前应自行阅读关键代码并复跑检查，尤其要能解释只读恢复事务、保存快照、索引同步和性能测量的边界。
